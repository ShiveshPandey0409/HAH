# Plan 01: user creation

## Scope

Implement one FastAPI use case:

```text
POST /v1/users → validate input → insert user → return created user
```

This plan does not include login, authentication-provider integration, social
profiles, enrichment, tasks, bounties, MCP, verification, Prava payments, workers,
or webhooks.

## Authentication addendum

The original user-creation milestone was intentionally internal and unauthenticated.
Before public deployment it was superseded by `POST /v1/auth/signup`. The current
account lifecycle is signup, login, me, logout, change password, forgot password,
and reset password. Passwords use salted scrypt hashes; login and reset credentials
are stored only as SHA-256 hashes. Business endpoints derive the actor from the
revocable session instead of accepting a user ID. MCP OAuth identities and browser
sessions both reference the same `users.id`.

## User fields

The endpoint uses the existing `users` table.

| Field | Input | Rule |
|---|---|---|
| `email` | Required | Valid email and unique, stored case-insensitively |
| `display_name` | Required | Trimmed and cannot be empty |
| `can_create_tasks` | Required | `true` when the user can create tasks |
| `can_work_tasks` | Required | `true` when the user can work as a freelancer |
| `bio` | Optional | Short profile text |

At least one of `can_create_tasks` or `can_work_tasks` must be `true`. A user can
have both capabilities.

The following are not part of user creation:

- user status;
- trust score;
- Reddit or LinkedIn URL;
- Prava account reference;
- password or authentication-provider fields.

`id`, `created_at`, and `updated_at` are generated by PostgreSQL.

## API contract

### Request

```http
POST /v1/users
Content-Type: application/json
```

Creator example:

```json
{
  "email": "creator@example.com",
  "display_name": "Campaign Creator",
  "can_create_tasks": true,
  "can_work_tasks": false,
  "bio": null
}
```

Freelancer example:

```json
{
  "email": "worker@example.com",
  "display_name": "Marketing Freelancer",
  "can_create_tasks": false,
  "can_work_tasks": true,
  "bio": "Reddit and LinkedIn marketing"
}
```

### Successful response

Return HTTP `201 Created`:

```json
{
  "id": "7e2090fc-4137-443d-a736-d07e7ae5dd13",
  "email": "worker@example.com",
  "display_name": "Marketing Freelancer",
  "can_create_tasks": false,
  "can_work_tasks": true,
  "bio": "Reddit and LinkedIn marketing",
  "created_at": "2026-08-01T18:00:00Z",
  "updated_at": "2026-08-01T18:00:00Z"
}
```

Do not return internal Prava fields from this endpoint.

### Errors

| HTTP status | Condition |
|---|---|
| `409 Conflict` | Email already exists |
| `422 Unprocessable Entity` | Invalid email, empty name, or both capabilities are false |
| `500 Internal Server Error` | Unexpected database failure; log the request ID, not sensitive input |

## Step-by-step implementation

### Step 1: Create the FastAPI foundation

1. Add FastAPI, Uvicorn, SQLAlchemy, asyncpg, Pydantic Settings, and Alembic.
2. Create `backend/app/main.py`.
3. Configure `DATABASE_URL` through environment settings.
4. Create one SQLAlchemy `AsyncSession` per request.
5. Add a basic `/health` route.

Done when FastAPI starts and can connect to PostgreSQL.

### Step 2: Add the user database mapping

1. Map the existing `users` table in `backend/app/models/user.py`.
2. Keep PostgreSQL responsible for UUIDs, timestamps, case-insensitive email,
   uniqueness, and the capability check.
3. Load the authoritative `database/schema.sql` baseline into an empty PostgreSQL
   database and stamp Alembic revision `20260801_0001`.
4. Apply only later schema changes through new Alembic migrations.

Done when a user can be inserted directly through SQLAlchemy.

### Step 3: Add request and response schemas

Create:

- `UserCreate`: accepted request fields;
- `UserResponse`: safe returned fields.

Pydantic must:

1. validate and normalize the email;
2. trim `display_name`;
3. reject an empty display name;
4. reject requests where both capability flags are false.

Done when schema unit tests cover valid creator, freelancer, and dual-capability users.

### Step 4: Add the creation service

`create_user(session, data)` must:

1. create the SQLAlchemy user model;
2. flush the insert inside the request transaction;
3. translate the unique-email database violation to a domain conflict;
4. commit once;
5. refresh and return the created row;
6. roll back on failure.

The service owns this behavior so a future MCP or admin surface can reuse it
without calling the HTTP route.

Done when the service returns the database-generated UUID and timestamps.

### Step 5: Add `POST /v1/users`

1. Create the users router.
2. Inject one request-scoped database session.
3. Accept `UserCreate`.
4. Call the creation service.
5. Return `UserResponse` with HTTP `201`.
6. Convert duplicate email to HTTP `409`.
7. Register the router under `/v1`.

Done when the endpoint appears correctly in FastAPI OpenAPI documentation.

### Step 6: Test the endpoint

Add tests for:

- creating a task creator;
- creating a freelancer;
- creating a user with both capabilities;
- normalizing email case;
- duplicate email rejection;
- empty display-name rejection;
- invalid email rejection;
- both capabilities set to false;
- generated UUID and timestamps;
- response excludes Prava fields;
- transaction rollback after a database error.

Use a real temporary PostgreSQL database for integration tests so `citext`, UUID
defaults, and database constraints are actually exercised.

Done when all tests run from a clean database without manual data setup.

## Work that can happen in parallel

After the FastAPI/database session foundation exists, three small tasks can run in
parallel:

| Workstream | Deliverable |
|---|---|
| Database | SQLAlchemy user mapping and Alembic migration |
| API | Pydantic request/response schemas and users router |
| Quality | PostgreSQL test fixture and user-creation test cases |

The creation service joins these three pieces. Do not start other product domains
until this endpoint passes its integration tests.

## Definition of done

User creation is complete when `POST /v1/users` creates creator, freelancer, or
dual-capability users; returns only safe user fields; rejects duplicates and invalid
capability combinations; and passes all tests against a clean PostgreSQL database.
